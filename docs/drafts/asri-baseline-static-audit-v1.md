# Asri Collection Baseline — Static Audit V1

- Repository: `gantulu/ws`
- Branch: `feat/store-mobile-v1-app`
- Status: **STATIC REVIEW COMPLETE WITH CONDITIONS — NOT APPROVED FOR MIGRATION PROMOTION**
- Scope: `docs/drafts/asri-catalog-baseline-review.sql` and `docs/drafts/asri-payment-baseline-review.sql`
- Safety: review only. No Supabase project was created or changed, and no migration was executed.

## Evidence source

The two drafts were compared against the audited legacy tables in the connected shared project using read-only schema queries: columns/defaults, constraints, indexes, RLS policies, triggers, grants, and row counts. The five legacy Asri tables had zero rows at the last check. Do not copy data from unrelated generic `products` tables into Asri.

## Catalog baseline — findings

### Passes
- Preserves audited `asri_products` column names and core defaults, including nullable unique `sku`/`slug`, IDR currency, image/variant JSON fields, nonnegative price/stock, and compare-at-price constraints.
- Preserves the public-read-only model for active products; RLS is enabled, anon/authenticated receive SELECT only, and the policy filters to `is_active = true`.
- Adds a deterministic `updated_at` trigger with a restricted function search path.
- No product fixture or seed data is inserted by the draft.

### Conditions before promotion
1. Validate `gen_random_uuid()`, trigger creation, RLS and role grants on the exact local Supabase/Postgres version used by the target project.
2. Confirm the storefront's actual catalogue query and sorting requirements. The two new partial indexes are reasonable candidates, but they should be justified by query plans before production scale.
3. Test that anon/authenticated cannot read inactive products or write any product fields, while service_role can perform intended server-side writes.
4. Verify the trigger changes `updated_at` on update and that transaction rollback leaves no fixtures behind.

## Payment baseline — findings

### Passes
- Preserves the audited four-table model and relevant column names/defaults.
- Preserves amount > 0, IDR-only currency, expiry > 0 when set, known payment statuses, callback processing statuses, and status-history source constraints.
- Preserves the audited partial unique indexes for provider reference and callback fingerprint, including their non-null predicates.
- Enables RLS and explicitly revokes client-role access to all payment tables; only `service_role` receives table privileges.
- Keeps callbacks without an order foreign key so a verified/rejected unmatched provider callback can still be recorded for investigation; application code must not treat that as a valid payment.

### Conditions before promotion
1. The draft intentionally changes `asri_payment_status_history.id` to `GENERATED BY DEFAULT AS IDENTITY`; verify that this is the desired correction and test insert/sequence behavior. It is not byte-for-byte schema parity with the legacy table.
2. The draft does not add `updated_at` triggers to payment tables. The read-only audit did not find such triggers on the legacy payment tables; do not assume automatic timestamps.
3. The partial unique index on `(provider, provider_reference)` must be tested against every upsert conflict target. PostgreSQL may require a matching predicate for partial-index inference.
4. Test that duplicate non-null callback fingerprints fail safely or are handled idempotently by the application, and that null fingerprints remain allowed.
5. Test payment order/transaction/status-history foreign keys, invalid statuses, zero/negative amounts, duplicate merchant order IDs, and client-role denial.
6. Confirm the exact Edge Function insert/update patterns against these columns before backend deployment. A schema pass alone does not validate callback correctness.

## Cross-cutting blockers

- There is no committed `supabase/config.toml` or canonical `supabase/migrations/` baseline in this branch yet.
- The live project's historical migration ledger includes unrelated application history and must not be copied wholesale into the new project.
- The Store V2 draft depends on both baseline migrations. It must be reviewed separately after the baseline passes.
- The Store V2 review SQL has an apparent PL/pgSQL delimiter defect in `asri_store_reject_history_mutation()` (the body opens with `as $` rather than a paired `as $$`). Fix and re-test that separate draft before combining it with baseline DDL.
- Schema DDL does not implement the required atomic order creation / stock reservation transaction. A reviewed server-side transaction/RPC and concurrency tests remain mandatory.
- Secrets and hosted project configuration have not been verified. Do not print secret values.

## Promotion gate

Do not move either draft into `supabase/migrations/` until:
- the isolated local test plan is completed against a clean local Supabase stack;
- all assertions in `asri-baseline-isolated-assertions.sql` pass;
- SQL errors and privilege/policy failures are fixed;
- the final diff and the exact tested SQL hashes are recorded;
- Store V2 dependencies and payment Edge Function contract are reconciled.
